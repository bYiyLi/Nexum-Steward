## 管理运维规范

### 运维目标

本服务器用于功能测试、集成测试和质量验证。优先保证测试环境可复现、测试证据可信以及问题能够重现。

### 服务管理

- 仅管理目标 Nexum Agent 所在服务器的本机 Docker Engine。向 Daemon 发起请求前，核实 context、环境变量及参数覆盖后的实际 endpoint 和本机归属；远程或无法确认时停止相关 Docker 操作，不以命令成功代替归属证据，也不自动切换或改写连接。执行身份或连接条件改变后重新核验。

- 所有由 Steward 管理的服务位于 Services Root 下，各服务使用独立的 Docker Compose 项目。
- 使用来源明确、可追溯的镜像或构建产物；每次测试应能识别所使用的服务版本和配置状态。
- 测试正在进行时，不得擅自更新、重启或替换其依赖的服务；变更前应确认当前测试的影响与授权范围。
- 调整配置或服务运行状态时，明确是否改变了当前测试基线。

### 配置管理

- 配置 Git 用于追溯和重建材料同步，不是数据备份；纳入 Compose、非敏感配置/样例、必要说明及脱敏 `logs/YYYY-MM-DD.md`，排除 data、备份、数据库、应用运行日志、缓存和镜像产物。
- 推荐独立私有仓库；共享时明确受管子路径与分支/权限，不混入其他机器/用户改动。首次确认远程 URL、owner/org、可见性、分支、范围和同步授权，不猜目标、不自动建远程或凭证。
- 按内容判断 `.env`：非敏感可提交，敏感优先用现有可信加密方案；密钥不与密文同库，核实安全获取/恢复，缺能力报告、不造算法。默认不提交明文秘密，私有仓库不放宽保护；远程发送须按宿主对具体数据/目标/风险逐次确认。
- 有意义且检查完成的变更及时定向提交，核对本地/远程及实际 staged diff，不暂存全工作区；已确认授权内及时推送并核对远端。保留用户修改，不强推/重写/自动清冲突；失败保留提交、不换账号目标或无限重试。分报修改/提交/同步与业务验证，必需远程留档失败阻塞该项；完整规则由 steward-spec 持有。
- 测试期间保持已确认的配置基线。需要调整时，记录变更原因、配置版本以及受影响的测试。
- 临时排障修改不得悄悄成为新的测试基线。
- 测试失败时，优先保留用于重现问题的配置、日志和版本信息。

### 测试数据管理

- 持久数据默认优先使用 `Services Root/<服务名>/data` + bind mount；命名/匿名卷仅作为有依据的例外，保护既有数据、不自动迁移，data 不进入配置 Git。完整共同约定由 steward-spec 持有。

- 明确测试数据的来源、用途以及是否允许重建。
- 可在已授权的测试范围内重置指定测试数据，不清理无关数据。
- 不直接使用未经适当脱敏和授权的生产数据。
- 重置后应能重新建立本次测试所需的基础状态；无法恢复时应报告阻碍。

### 验证与记录

- 服务更新后核对实际运行版本、配置和健康状态；区分环境故障、部署失败和业务测试失败。
- 将影响测试环境的重要操作、配置版本、结果与异常证据记录到 Services Root 的 `logs/YYYY-MM-DD.md`。按服务器时区使用 `### <ISO 8601 时间> · <目标>` 作为条目标题，记录操作、结果、验证以及适用的 Git Commit（没有则写「未提交」）和恢复信息；不记录秘密。
- 若配置变化导致测试结果无法与原基线比较，明确标注结果不可比。
- 只有环境满足本次测试的必要条件，才能报告测试环境准备完成。
