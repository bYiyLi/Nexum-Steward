## 管理运维规范

### 运维目标

本服务器用于功能测试、集成测试和质量验证。优先保证测试环境可复现、测试证据可信以及问题能够重现。

### 服务管理

- 所有由 Steward 管理的服务位于 Services Root 下，各服务使用独立的 Docker Compose 项目。
- 使用来源明确、可追溯的镜像或构建产物；每次测试应能识别所使用的服务版本和配置状态。
- 测试正在进行时，不得擅自更新、重启或替换其依赖的服务；变更前应确认当前测试的影响与授权范围。
- 调整配置或服务运行状态时，明确是否改变了当前测试基线。

### 配置管理

- 使用 Services Root 的本地 Git 管理非敏感配置；不自动推送远程 Git，不以明文提交密钥。
- 测试期间保持已确认的配置基线。需要调整时，记录变更原因、配置版本以及受影响的测试。
- 临时排障修改不得悄悄成为新的测试基线。
- 测试失败时，优先保留用于重现问题的配置、日志和版本信息。

### 测试数据管理

- 明确测试数据的来源、用途以及是否允许重建。
- 可在已授权的测试范围内重置指定测试数据，不清理无关数据。
- 不直接使用未经适当脱敏和授权的生产数据。
- 重置后应能重新建立本次测试所需的基础状态；无法恢复时应报告阻碍。

### 验证与记录

- 服务更新后核对实际运行版本、配置和健康状态；区分环境故障、部署失败和业务测试失败。
- 将影响测试环境的重要操作、配置版本、结果与异常证据记录到 Services Root 的 `logs/YYYY-MM-DD.md`。按服务器时区使用 `### <ISO 8601 时间> · <目标>` 作为条目标题，记录操作、结果、验证以及适用的 Git Commit（没有则写「未提交」）和恢复信息；不记录秘密。
- 若配置变化导致测试结果无法与原基线比较，明确标注结果不可比。
- 只有环境满足本次测试的必要条件，才能报告测试环境准备完成。
