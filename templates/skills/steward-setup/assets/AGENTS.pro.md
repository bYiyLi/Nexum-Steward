## 管理运维规范

### 运维目标

本服务器用于正式发布前的部署验证、升级演练及恢复演练。优先验证计划中的生产变更是否具备上线条件。

### 服务管理

- 运维单元按用途、生命周期及影响边界划分，不等于单容器；默认直接使用 `Services Root/<单元名>/`，主 `compose.yaml`、自有配置/秘密引用/数据同属该目录，具有独立稳定的 Compose 项目身份；同单元多文件须明确顺序及相对路径基准。不强制预建 config/secrets/data 空目录。
- 应用与专用数据库/缓存可在同一单元，共享数据库独立归属；不能仅为统一启动或共享网络集中到 edge。共享网络/入口/存储须明确创建/维护归属、消费者和变更影响，不强制全局网络。已有布局先评估，需迁移时计划获批后才执行，不倒推旧部署违规；保护项目名、相对路径、数据/证书、共享资源及用户定制。完整规则与案例由 steward-spec 持有。

- 仅管理目标 Nexum Agent 所在服务器的本机 Docker Engine。向 Daemon 发起请求前，核实 context、环境变量及参数覆盖后的实际 endpoint 和本机归属；远程或无法确认时停止相关 Docker 操作，不以命令成功代替归属证据，也不自动切换或改写连接。执行身份或连接条件改变后重新核验。

- 预生产环境应尽可能与生产环境保持一致的服务拓扑、软件版本、Compose 配置结构和部署方式。比较时只能使用用户提供或当前授权范围内可读的生产基线；基线不可得时说明差异未验证，不猜测生产配置或访问未授权的生产 Agent。
- 使用明确的发布候选镜像或构建产物；不随意引入未经确认的版本，不把开发调试配置直接用于预生产。
- 不以预生产环境的名义修改真实生产服务。

### 发布演练

- 按计划中的生产发布步骤执行预生产部署，检查配置、镜像版本、挂载、端口、网络及依赖。
- 验证启动结果、应用健康和必要业务流程；若需要临时人工干预，记录干预步骤及原因。
- 涉及数据迁移时，使用适当的预生产数据验证迁移及恢复条件；不能把镜像回退当作数据恢复。
- 发现阻断发布的问题时，保留证据，报告演练未通过，不自动继续生产发布。

### 配置与数据

- 持久数据默认优先使用 `Services Root/<单元名>/data` + bind mount；已有外部路径、命名/匿名卷或软件要求作为说明理由的例外，保护既有数据、不自动迁移，data 不进入配置 Git。完整共同约定由 steward-spec 持有。

- 配置 Git 用于追溯和重建材料同步，不是数据备份；纳入 Compose、非敏感配置/样例、必要说明及脱敏 `logs/YYYY-MM-DD.md`，排除 data、备份、数据库、应用运行日志、缓存和镜像产物。
- 推荐独立私有仓库；共享时明确受管子路径与分支/权限，不混入其他机器/用户改动。首次确认远程 URL、owner/org、可见性、分支、范围和同步授权，不猜目标、不自动建远程或凭证。
- 文件按内容与用途分类，不仅凭目录名：人工非敏感配置可提交，证书/私钥、秘密、运行状态及业务数据按既有安全规则处理，放在 config 下也不例外。按内容判断 `.env`：非敏感可提交，敏感优先用现有可信加密方案；密钥不与密文同库，核实安全获取/恢复，缺能力报告、不造算法。默认不提交明文秘密，私有仓库不放宽保护；远程发送须按宿主对具体数据/目标/风险逐次确认。
- 有意义且检查完成的变更及时定向提交，核对本地/远程及实际 staged diff，不暂存全工作区；已确认授权内及时推送并核对远端。保留用户修改，不强推/重写/自动清冲突；失败保留提交、不换账号目标或无限重试。分报修改/提交/同步与业务验证，必需远程留档失败阻塞该项；完整规则由 steward-spec 持有。
- 记录演练配置版本及与生产的差异；不直接复用生产凭证，也不使用未经授权或保护的真实用户数据。
- 未明确授权时不清理现存持久化数据、测试结果或备份。

### 验证与记录

- 验证适用的恢复、回退步骤及其前提条件，不将未经运行的步骤描述为已验证。
- 将发布候选版本、演练步骤、实际结果、异常及生产差异记录到 Services Root 的 `logs/YYYY-MM-DD.md`。按服务器时区使用 `### <ISO 8601 时间> · <目标>` 作为条目标题，记录操作、结果、验证以及适用的 Git Commit（没有则写「未提交」）和恢复信息；不记录秘密。
- 未完成关键验证时，明确标记发布条件尚未满足。
- 预生产验证通过仅证明实际演练范围通过，不自动授权正式生产发布。
