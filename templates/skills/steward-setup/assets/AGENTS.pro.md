## 管理运维规范

### 运维目标

本服务器用于正式发布前的部署验证、升级演练及恢复演练。优先验证计划中的生产变更是否具备上线条件。

### 服务管理

- 仅管理目标 Nexum Agent 所在服务器的本机 Docker Engine。向 Daemon 发起请求前，核实 context、环境变量及参数覆盖后的实际 endpoint 和本机归属；远程或无法确认时停止相关 Docker 操作，不以命令成功代替归属证据，也不自动切换或改写连接。执行身份或连接条件改变后重新核验。

- 预生产环境应尽可能与生产环境保持一致的服务拓扑、软件版本、Compose 配置结构和部署方式。比较时只能使用用户提供或当前授权范围内可读的生产基线；基线不可得时说明差异未验证，不猜测生产配置或访问未授权的生产 Agent。
- 使用明确的发布候选镜像或构建产物；不随意引入未经确认的版本，不把开发调试配置直接用于预生产。
- 不以预生产环境的名义修改真实生产服务。

### 发布演练

- 按计划中的生产发布步骤执行预生产部署，检查配置、镜像版本、挂载、端口、网络及依赖。
- 验证启动结果、应用健康和必要业务流程；若需要临时人工干预，记录干预步骤及原因。
- 涉及数据迁移时，使用适当的预生产数据验证迁移及恢复条件；不能把镜像回退当作数据恢复。
- 发现阻断发布的问题时，保留证据，报告演练未通过，不自动继续生产发布。

### 配置与数据

- 使用 Services Root 的本地 Git 管理非敏感配置历史，记录演练使用的配置版本及与生产的差异；不自动推送远程 Git。
- 不直接复用生产凭证，也不使用未经授权或保护的真实用户数据；含敏感值的 `.env` 不以明文纳入 Git。
- 未明确授权时不清理现存持久化数据、测试结果或备份。

### 验证与记录

- 验证适用的恢复、回退步骤及其前提条件，不将未经运行的步骤描述为已验证。
- 将发布候选版本、演练步骤、实际结果、异常及生产差异记录到 Services Root 的 `logs/YYYY-MM-DD.md`。按服务器时区使用 `### <ISO 8601 时间> · <目标>` 作为条目标题，记录操作、结果、验证以及适用的 Git Commit（没有则写「未提交」）和恢复信息；不记录秘密。
- 未完成关键验证时，明确标记发布条件尚未满足。
- 预生产验证通过仅证明实际演练范围通过，不自动授权正式生产发布。
