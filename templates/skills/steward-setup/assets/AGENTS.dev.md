## 管理运维规范

### 运维目标

本服务器用于开发、调试与功能验证。优先支持快速迭代，同时保护现有配置和有价值的开发数据。

### 服务管理

- 所有由 Steward 管理的 Docker Compose 服务位于 Services Root 下，每个服务使用独立目录。
- 用户授权开发任务后，可在该任务范围内自主修改 Compose 配置、构建镜像、更新、重建及重启目标服务，无须逐条询问。
- 可以按任务需要使用本地构建、源码挂载、调试配置及 Compose Watch。
- 不修改无关服务，不默认升级整台服务器，也不因开发便利自动开放公网管理接口、数据库端口或特权容器。

### 配置管理

- 修改前检查并保留已有配置和用户定制；修改 Compose 后先检查配置有效性，再执行服务操作。
- 使用 Services Root 下的本地 Git 管理非敏感配置与变更历史；不自动推送远程 Git。
- 不将密码、Token 等敏感值以明文提交到 Git；含密钥的 `.env` 需要独立安全存储或加密后管理。

### 数据管理

- 区分可重建的测试数据和需要保留的开发数据。
- 重置数据必须明确目标并获得相应授权；开发环境不等于可以销毁所有数据。
- 可能影响需要保留的数据时，先核实恢复条件；不把数据库运行数据放入配置 Git 仓库。

### 验证与记录

- 部署后检查 Compose 项目、容器状态及适用的服务可用性；命令成功不等于应用健康。
- 允许边调试边修复，但失败后要依据新的实际证据处理，不盲目重放操作。
- 将重要配置变更、服务操作及实际结果记录到 Services Root 下的 `logs/YYYY-MM-DD.md`。按服务器时区使用 `### <ISO 8601 时间> · <目标>` 作为条目标题，记录操作、结果、验证以及适用的 Git Commit（没有则写「未提交」）和恢复信息；不记录秘密。
- 报告真实完成内容和未解决的问题。
