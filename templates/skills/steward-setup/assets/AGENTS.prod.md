## 管理运维规范

### 运维目标

本服务器承载正式业务服务。优先保障服务连续性、数据完整性、变更可追溯及故障可恢复。

### 服务管理

- 仅管理目标 Nexum Agent 所在服务器的本机 Docker Engine。向 Daemon 发起请求前，核实 context、环境变量及参数覆盖后的实际 endpoint 和本机归属；远程或无法确认时停止相关 Docker 操作，不以命令成功代替归属证据，也不自动切换或改写连接。执行身份或连接条件改变后重新核验。

- 所有由 Steward 管理的服务位于已确认的 Services Root 下，使用明确、可追溯版本的镜像或构建产物；不做无目标版本的随意升级。
- 对已运行服务采取最小必要变更，不修改无关服务，不在生产环境进行临时开发或未经授权的实验。
- 停止、重启或替换服务前，应判断对正式业务、依赖服务及持续运行的工作负载的影响。
- 可能造成业务中断或显著改变服务行为的操作，必须在已确认的影响范围及必要授权下执行。

### 变更管理

- 计划变更前确认目标、当前版本、预期结果、影响范围与可行的恢复办法。
- 已获得明确授权的普通步骤可以连续执行，不必逐条重复询问；新出现的重大风险、范围变化及不可逆操作必须先取得相应授权。
- 修改 Compose 前检查现有配置、端口、网络、依赖和持久化数据挂载。
- 使用 Services Root 的本地 Git 保存非敏感配置的变更历史；不自动推送远程 Git、不重置历史，也不以明文提交秘密。

### 数据保护

- 影响持久化数据的操作前，识别数据位置、修改范围和潜在影响。
- 可能损害数据完整性或恢复能力时，先确认可用的备份与实际恢复条件，或取得用户对具体风险的明确决定。
- 不默认删除 Volume、数据库、备份或业务数据。
- 容器或镜像回退成功不能证明数据库及持久化数据已经恢复。
- 数据操作失败或结果未知时，停止后续依赖动作并检查实际状态。

### 故障处理

- 先识别故障范围，尽可能限制对正常业务的影响，并保留必要的状态、日志及配置证据。
- 原因不明时，不连续重启、重建或清理多个生产服务。
- 恢复前检查现有数据和依赖关系；结果未知时先核实，不盲目重放有副作用的命令。
- 无法安全恢复时，报告真实状态、风险及可行的恢复路径。

### 验证与运维记录

- 变更后检查 Compose 项目、容器、应用健康及受影响的业务功能。只能证明容器运行时，不得声称业务已恢复正常。
- 重要变更与故障恢复记录目标、时间、实际动作、配置版本、执行结果、验证证据及未解决风险。
- 将记录写入 Services Root 的 `logs/YYYY-MM-DD.md`。按服务器时区使用 `### <ISO 8601 时间> · <目标>` 作为条目标题，记录操作、结果、验证以及适用的 Git Commit（没有则写「未提交」）和恢复信息；不得写入密码、Token 或其他秘密。
- 未通过必要的业务验收时，不将生产变更报告为完成。
